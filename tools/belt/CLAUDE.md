# belt, Claude Code guard, hint and ledger hooks

Go CLI. Central hook binary for Claude Code sessions, with four concepts: **guards** inspect a tool call before it runs and deny risky ones with a reason the model reads. **Allows** run after every guard passed and may answer allow for one narrow, read-only call shape; each is off until the config turns it on. **Hints** inspect a tool call after it ran and add advisory context the model reads next to the result. **Ledger** entries record session lifecycle events (subagents, tasks, permission denials, notifications, compaction, session end, turns that died on an API error) to the events service and reach no model. One opt-in helper sits on the ledger's service: `belt watch` wakes an idle session when an item addressed to it arrives. Pairs with `suspenders` (the git-hook layer): suspenders guards commits, belt guards the session before anything reaches git.

The split is load-bearing (docs/adr/0008, docs/adr/0024, docs/adr/0032). A guard exists to prevent damage that is hard to undo. An allow exists to skip a prompt for a call that is provably a read; it has no denial path and runs only when no guard denied, so a deny always wins. A hint exists to improve a choice that was merely suboptimal, and a ledger entry exists to leave a record. A hint has no denial path in its interface, so it cannot block a tool call even by mistake. The record entrypoint has no output writer, so it cannot steer a session even by mistake. `belt watch` is the one command that exits 2, on purpose: that is the asyncRewake wake signal.

Born out of a July 2026 session retrospective: a session pushed straight to master and tried to self-merge, and internal names reached `git commit` twice before the pre-commit hook caught them. belt moves both checks to the earliest point a hook can intervene.

## How it works

`internal/hook` parses a PreToolUse payload from stdin, runs the guards registered for that event, and writes a deny decision to stdout. A payload it cannot read denies with `belt[payload]:` before any guard runs, like a broken config; `operating.md` (failure modes) states that rule in full. Deny always travels in `hookSpecificOutput.permissionDecision` with exit 0: a hook must not break tool calls on its own bugs, so the deny is data, not a process exit code. Guards for an event run in registration order and the first denial wins; every deny reason is prefixed `belt[<guard-id>]:` so a block is always attributable to the guard that fired. Only when `guard.RunClean` reports a clean pass (no denial, and no guard that failed open or warned in soft mode, seen through each guard's `emit`, or gave advice) does the hook run the enabled allows (`guard.Approve`); the first approval becomes `permissionDecision: "allow"` with a `belt[<allow-id>]:` reason, and an approval posts no event. A guard in hint mode (`config.HintModeGuards`) lets the call through with advice instead of a denial (`guard.Advice`, collected through the `adviser` interface by `guard.RunAdvised` and `guard.Verdict`). When no guard denied, the hook writes that advice as PreToolUse `additionalContext` with no permission decision (`adviseGuarded`), archives an `info` event per piece, and runs no allow. A denial from any guard drops the advice.

`internal/config` treats `~/.config/belt/config.yaml` as the belt-owned surface: per-guard toggles, exclude paths, extra patterns, `claude_settings`, and the `internal_names` section. That section may list shared names files under `include` (docs/adr/0016). Those files are belt-named surfaces read strictly, `blocked_words`/`allowlist`/`allow_phrases` only, and are appended to the section's own lists. `$XDG_CONFIG_HOME` moves the directory; `--config`/`$BELT_CONFIG` relocate the file itself. A legacy `config.toml` beside the default file is read only when the YAML file is absent. A present-but-broken file of either format never falls back to the other one.

The config is standalone and has no machine-profile concept (docs/adr/0010). belt never reads another tool's file, and an absent `internal_names` section means an empty name set. The provisioning layer renders one config per machine class. A guard or rule meant for only some machines is simply absent (or disabled) in the other classes' files. Exactly one non-belt surface is read: Claude Code's settings files, gated by `claude_settings.enabled` (default true). The hooks read the `permissions.deny` Bash entries of `~/.claude/settings.json` + `settings.local.json` live for the script guard (shared source of truth with the permission system). `belt doctor` also reads those two files' `hooks.PostToolUse` entries, only to check the `belt hint read` matcher. The agent-memory hint reads the auto memory keys, but only under `belt hint session-start --agent claude-code`, and from the files Claude Code reads them from: `~/.claude/settings.json`, the session's project files and the managed settings files, never `~/.claude/settings.local.json` outside a home-directory session (`config.ClaudeSources`, a list apart from the deny-list files). `belt doctor` reads them too, for its own working directory, plus the `hooks.SessionStart` entries of the two `~/.claude` files, to report a store that flag leaves out.

A missing config file yields the armed defaults with no error. A config file that is present and fails to parse or validate is an error `config.Load` returns. So is a names file listed under `internal_names.include` that is missing or broken. `belt hook` turns either into a `belt[config]:` deny on every tool call. belt cannot distinguish "no rules" from "the rules did not load", so it blocks rather than run unarmed (`doctor` and `config` still print, flagging that the state shown is the defaults). Validation covers the keys that parse and then do nothing:

- a `custom_guards.<name>` entry whose event is outside `bash`/`write` or whose command is empty;
- a `custom_hints.<name>` entry whose event is not `session-start` or `subagent-start`, whose command is empty, or whose name shadows a built-in hint;
- a `custom_hints.<name>.agent_types` key on a hint not on `subagent-start`, or one that is empty or holds a blank entry or one with a `*` before its end;
- `mode:` values that are neither `hard` nor `soft` or that sit on a guard outside `config.SoftModeGuards`, and on a guard in `config.HintModeGuards` (main-checkout) any value but `hint` or `deny`;
- a negative top-level `large_file_lines` (0 or unset means `config.DefaultLargeFileLines`, 300);
- a `guards.main-checkout.worktree_commands` entry with an empty, relative or repeated `path`, an empty `command`, or a `{...}` in it that names no placeholder.

The `ledger`, `watch` and `allows` sections (`internal/config/lifecycle.go`, `internal/config/allows.go`) are deliberately outside validation: a config error denies every guarded call, far too much for a typo in an optional feature. Their accessors clamp (poll floor 100 ms, max wait cap 1 h, negative means default) and rewrite sources the way the events service sanitizes them. `Adjustments()` names each change, and `belt doctor` warns with it. Only YAML type errors still fail the file. Keep it that way when adding a key to either section.

`ledger.agent_types` (`internal/config/agenttypes.go`) goes one step further: its own `UnmarshalYAML`/`UnmarshalTOML` decode any shape. A wrong type, a duplicate key, a `*` before a key's end, an effort outside low/medium/high/xhigh/max, or an empty model drops that entry or tag with an adjustment. So even a type error there cannot fail the file. `UnmarshalYAML` walks the mapping pair by pair on purpose: yaml.v3 fails a whole decode on one duplicate key, which would cost every valid entry beside it.

Rollout order: a binary older than a newly accepted config value (subagent-start, for one) rejects it and denies everything. So the fleet must `ralph up` the new belt before a machine config uses the value. A new key fails the other way, because the YAML decode drops unknown keys. An older belt ignores a custom hint's `agent_types` and runs the hint for every subagent, and ignores `guards.main-checkout.worktree_commands` and hands over the git command. It also ignores `ledger.agent_types` and records no model or effort. A belt that knows `agent_types` but not `*` matching reads a `*` entry literally, so a gated brief reaches no subagent until the new belt is installed. The same order applies. It applies to the `--agent` flag on `belt hint` as well: an older belt fails on the unknown flag, and the session starts with no session-start hints at all.

Every hook payload's identity reaches the checks: `session_id` always, `agent_id`/`agent_type` inside a subagent. They are copied into `guard.Input` and `hint.Input`, added to custom guard and custom hint stdin only when set (`guard.Identity.AddTo`), and tag every deny and hint event. The session and agent fields are `lenientString`: `belt hook` denies a payload it cannot decode (`belt[payload]`), so a field no guard reads must never fail that decode. The lifecycle-only fields live in `recordPayload` for the same reason. The fields the guards do read stay strictly typed: `tool_name`, `tool_input`, `cwd`, and the `tool_input` keys `guardInputFields` lists per event (`hintInputFields` is the hint twin). When `toInput` starts reading a new key, add it there, or a mistyped value reaches the guards as `""`.

### Guards

| id | event | rule |
|----|-------|------|
| `git-push-main` | `bash` | Deny `git push` targeting main/master unless the target repo is on the shared `direct_main_repos` list or the guard's `allow_repos` allowlist (`pushExempt`; both canonical `host/owner/repo`, e.g. `github.com/mad01/dotfiles`, or a trailing `/*` org wildcard, resolved from the push working dir's `origin` remote). Unresolved repos and off-allowlist repos fail closed; a machine class where direct pushes are fine disables the guard in its rendered config. Resolves bare `git push`/`HEAD` refspecs via `git rev-parse --abbrev-ref HEAD` in the payload cwd (or the `git -C` dir). A `git checkout` or `git switch` earlier in the command changes that (`headTracker`, `gitpushhead.go`) when it runs in the push's own known directory (`knownDir`: the same `-C` target or `cd` state, a subshell included; a switch in another or an unknown directory adds no branch for the push, but as the command's last switch it leaves an earlier one in the push's directory unsure): the push is judged on the branch git reads and on every branch a switch there may have moved to, latest first. A default name counts as that branch (`switchedDefaultDenial` names the switch), and one belt cannot read (a variable, `-`, `--detach`, an option it does not know) is unknown, denied wherever the push needs the current branch (`unreadSwitchDenial`). A short-option bundle (`-qc`) reads letter by letter when every letter is known (`readShort`). In an exempt repo a switch never turns an allow into a denial: a push the switches would deny is judged on the branch git reads alone. Only a sure switch replaces the branch git reads: `switch`, `checkout -b`/`-B`/`--orphan`/`--track`, or `checkout <name>` when the push repo has `refs/heads/<name>` at check time, since git then never reads `<name>` as a path. That is the one git call the guard makes for a switch (`gitHasBranch`, injectable as `resolveHasBranch`): `for-each-ref` in the push's own directory under `branchLookupTimeout` (2 s), where an error or a timeout counts as no branch. It must run git plainly, with only assignments and `wrapperOptions` wrappers before the git word, none of them async (`coproc`, `setsid`, `wrapperSpec.async`, which may leave the switch running), and no `!` (`runsGit`), not after `\|\|` or a pipe, with `&&` alone joining it to the push (`walkStep.chain`). It must be the command's last switch, and every step between it and the push and after the push must be on one list (`keepsHead`): `headKeepers` git subcommands (add, commit, fetch, pull, merge, status, log, diff) run plainly, `git rebase` with at most one upstream (`rebaseKeepsHead`), a whole `currentBranchCommands` read, or a `readOnlyCommands` command. A listed git step with a `-c` override of its own, an `--output` option or a word naming a path inside `.git` does not count (`gitKeepsHead`), and a shell function defined anywhere in the command (`name() { …; }` or `function name { …; }`, `definesFunction`) makes no push sure (`headTracker.settle`). Anything else, an unknown command included, keeps the branch git reads as a candidate, since a step after the push may run beside it after `&` or in a pipeline (`pushHeads.afterPush`). The denial names the step that broke it (`unsureSwitchDenial`). A file checkout moves nothing, and a `prose` one counts not at all. Tracks `cd`/`pushd` across the command's segments, expanding a leading `~`, `$HOME`, or `${HOME}` in a cd target and a `git -C` target alike, and sending a bare `cd` home. A variable the command sets to a plain literal path (`S=~/repo; git -C $S push`, `${S}` and `"$S"` too) is substituted first (`resolveLiteralVars` in `gitutil.go`, shared by every `walkSegments` caller). That happens only when nothing could leave it empty or change it before the use. The name gets one assignment, at the start or after a `;` or newline, with no quote before it. The command must also hold no heredoc, subshell, brace group, comment, backslash, glob, keyword, other variable, zsh modifier like `$S:h`, or builtin such as `eval`, `read` or `source`; otherwise every variable stays as written. A cd or `-C` target only a shell can resolve leaves the directory unknown, as do `popd`, a bare `pushd`, `cd -P`, and `--git-dir`/`--work-tree`, and a default-branch push from an unknown directory is denied with a hint. A cd the shell may not run as written is unknown too: `cd +1`, `chdir`, any word before cd but `builtin`, a cd after `||` or in a pipeline, or a relative target while CDPATH is set. So is git with `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR` or `env -C`, and a push where git reads no branch, as after a failed cd and `;`. A `-C` path is handed to git as written, since git resolves `..` physically where a shell's cd is logical. git never runs in belt's own process cwd to fill the gap. Reads the push out of a wrapper too (`gitpush.go` over the `shellwalk.go` walk): a `( … )` subshell, a `$(…)`/backtick substitution (a substitution walked as the command it runs, `piece.code`: a backtick body loses one level of escapes, `backtickCode`, and inside double quotes the backslash of `\"` too, so nested backticks are read at every level; a backslash-newline between `$` and `(` joins them outside single quotes, `joinedAt`, as bash reads them), an `sh -c`/`bash -c` string, an `eval`, a `\`-continued line, or a `{ … }` group exposes the push to the same walk. An eval, a shell that reads its script and an xargs are found past the reserved words that open a command (`runAt`: `{`, `!`, `if`, `then`, `else`, `do`, `time`, the function keyword and a `case x in` head), so one inside a group, a loop, an if or a case arm reads as it does at the top level, and a function's body is read where it is defined, called or not (`bodyOf`). The walk also reads what a command hands a shell to run (`shellfeed.go`, `feedsOf`): a git alias body (`gitalias.go`, a `!` body read as shell text) for a name the command sets config for (`noteAliasConfig`: the invocation's own `-c`/`--config-env` key, a `GIT_CONFIG_KEY_<n>` or `GIT_CONFIG_PARAMETERS` assignment, or the key of a `git config` write, `readConfigSet`; a config read, an unset, and `alias.<name>` in free text name none, and a key with an expansion may name any, `walkMemory.anyAlias`), never for a `gitBuiltins` subcommand, which git runs before any alias; text `echo`, `printf` or a `cat` of a heredoc or here-string prints into a shell through a pipe, a here-string, a `<( )` operand or `source`/`.`, or into an xargs that runs its items as a shell's script (`xargsFeeds`: `xargs -0 sh -c`, `xargs -I{} sh -c {}`; each item cut as xargs cuts it, `xargsItems`, and read alone or in place of `-I`'s string); such text in a `-c` script, an `eval` (a backtick printer read as the command it runs, `wordPart.code`, as the walk reads it, so `` eval "`echo \"true; git push …\"`" `` runs the push), or a variable the command sets (`walkMemory.vars`), that variable as the command word too (`varCommandFeed`); and a file the command writes with a redirect or `tee`, then runs. Text it cannot read there makes the command opaque (`walkStep.opaque`, judged by `opaqueDenial`). An alias the command sets with no readable body and text past the per-command count below are denied on any branch, an exempt repo included. Everything else is `opacity.scoped`: shell text it cannot read (printed text holding a variable or a command's output, anything but a printer piped into a shell or into such an xargs), a non-shell interpreter script (heredoc, `-c`/`-e`, standard input, a written file with a shebang) that holds a process-starting word of its language (`processCalls`) and names `git` then `push` (`mentionsPush`, `scriptGitWord`), a script argument run as code inside a script that has some (`shellWalk.positional`, `runsPositional`), an argument an eval or a `-c` runs as its text after a function definition (`shellWalk.afterFunction`, `runsPositionalText`), and a variable or written file past `maxDerivedText` (64 KiB) or text past `maxDerivedBytes` (512 KiB) per command (`walkMemory.keep`). It is denied only in a repo with no direct-push exemption or from an unknown directory. Outside any git repo and in an exempt repo it is allowed. `resolveInRepo` (`gitInRepo`) runs `git rev-parse --git-dir` from the nearest existing directory above the push's under `branchLookupTimeout`; only exit 128 with "not a git repository" reads as outside, and any other failure or a timeout reads as inside. A `$( )` or `<( )` of any other command (`eval "$(ssh-agent -s)"`, `source <(fzf --zsh)`) keeps its old reading. These reads only add steps, at most `maxDerivedTexts` (64) texts per command. A command the reader cannot follow gets the full walk on its whole lines before the line it fails on, since bash runs those lines. The rest is read fail-closed (`walkUnread`): quotes dropped and every bracket read as a separator, so a git word and a push there deny unless the refspecs name a non-default branch in plain text. Nesting past `maxShellNesting` (32) levels reads the same way, so a crafted command costs no quadratic walk. A refspec word that is not plain text (a variable, a substitution, `$'...'`, a brace or a glob) may name main, so the push is denied wherever it runs. The exception is a whole-word `"$(git branch --show-current)"`, `git rev-parse --abbrev-ref HEAD` or `git symbolic-ref --short HEAD` substitution without `git -C`, which reads as the current branch. So does a `$NAME` refspec that `branchVars` (`gitpushvar.go`) vouches for: a lone top-level `NAME=` of one of those forms before the push, joined by start, `;`, newline or `&&`, NAME used nowhere else but as whole refspecs, not shell-managed, and unset in the environment after `&&`, in a command with no cd, pushd or popd, no `shellDenyWords` word, `.` or brace group. `@` reads as `HEAD` and `heads/<name>` as `refs/heads/<name>` (`destBranch`). A push that sweeps branches it does not name counts as a push to main (`pushSweep`, `gitpushargs.go`; `sweepDenial`): `--mirror`, `--all` or `--branches` by any unique prefix (`longPushOption`), and the matching refspec `:` or `+:`. An exempt repo takes them only through plain origin. So does a push with no refspec when a `-c` or `--config-env` key may pick its refspecs (`sweepConfigKey`: `push.default` but simple, current or nothing, `remote.<name>.push`, `remote.<name>.mirror`, `branch.<name>.merge`, `include.path` or `includeIf.<condition>.path`, or a key only a shell expands), or when the command sets config another way (`gitInvocation.setsConfig`: a `retargetsPush` step, a `GIT_CONFIG*`, `HOME` or `XDG_CONFIG_HOME` assignment, or sudo, doas or su before git, `setsConfigEnv`). A push with a refspec that has no `:dst` counts the same way, since git maps one through `remote.<name>.push` or an upstream push (`mappedRefspec`, `remapConfigKey`: `remote.<name>.push` whose destination may be main or master, `push.default` upstream or tracking, `branch.<name>.merge`, an include, or `setsConfig`). A refspec with a `:dst` and `--delete` map nothing. Config set before the command is out of reach. `parsePushArgs` reads options as git's parse-options does: short bundles, a value option that takes the next word even when it is `--`, and `--` or `--end-of-options` ending them. A word outside the refspecs that is not plain text (an option, its value, the remote, or a subcommand word with `push` after it, `hidesPush`) may turn into any option, so the push is denied wherever it runs (`shellWordDenial`). A heredoc body that `cat`, `tee`, `head`, `tail`, a git command that reads it as its message (`readsMessage`: `git commit`, or `git tag`, `git merge` or `git notes add` with `-F -`, `--file=-` or `-F /dev/stdin`) or a `gh pr|issue|release|gist|api` call only reads is prose (`docRuns`), walked the token way with its steps marked `prose`. So is a body piped from `cat` into a `gh pr create\|comment\|edit` or `gh issue create\|comment` that reads it with `--body-file -` or `-F -` and pipes nothing on (`readsBody`). Any other body, one piped on otherwise or written to a `>( )`, and every body in a substitution a `-c` script, eval, source or interpreter runs (`runsText`, `shellWalk.feeds`) is walked as code. An unquoted body's `$( )` and backticks are always walked as code (`bodySubstitutions`), found the way the shell expands the body. Its backslash-newlines are dropped first (`joinedBody`), so `$\` at a line end and `(…)` on the next line is a substitution. A backtick body closes at the first backtick no backslash quotes and loses one level of `\$`, `` \` `` and `\\` escapes (`backtickCode`), so a nested `` \`…\` `` in it is walked as code too. A `\"` keeps its backslash there, as in a bare word. The reader also joins a backslash-ended body line to the next before comparing it with the delimiter (`bodyLine`), as bash and zsh do. A git message is not walked at all: the heredoc a `git tag` or `git notes add` reads as its `-F -` file (`readsGitMessage`), and a `git commit -m "$(cat <<'EOF' ... EOF)"` substitution whose body the shell passes on as written (`messageCats`, `dataCat`), both only for a `shellWalk.plainGit` call: bare `git` first, depth 0, no `feeds`, no `cdHidden`, no redirect but its heredocs, no `runsText`, nothing but `-C DIR` before the subcommand (`plainSubcommand`), no numbered redirect such as `3<<` (`shellCmd.numbered`), and every word after `git` literal with its `token` equal to that literal, bar a `-m` value, which may also hold a quoted `$( )` (`plainArgs`). A `git commit` or `git merge` `-F -` heredoc keeps the token walk: both refresh the index before they read the message, and a `core.fsmonitor` program then runs with git's stdin. Both forms need every option on the per-subcommand allow list (`messageArgs`, `messageOptions`), which skips each `-m` or `-F` value as git does: `-e`, `-p` or any unknown option may start an editor or a prompt, so those bodies keep the token walk too. The `-m` form also needs `bash32Closes`: bash 3.2 knows no heredoc in a `$( )` and ends it at the first `)` its parse step or its expansion cannot match. A `$( )` bash 3.2 never closes in the walk's whole input (`shellWalk.input`, `bash32Unclosed`) is a syntax error that runs nothing, so it passes too. Any command's `$(cat <<'EOF' ... EOF)` that bash 3.2 may run more of than `cat` (`bash32Cats`) is read fail-closed (`walkUnread`), its steps marked `walkStep.bash32`, so a git-push-main, git-discard or file-discard denial there ends in `bash32Hint` (`bash32Hinted`). An unquoted body's `$( )` and backticks are still code. The repo exemption needs a push that plainly goes to `origin`: a URL, a second remote name, `--repo`, `-c remote.origin.pushurl=`, `-c url.*.pushInsteadOf=`, or a `GIT_CONFIG*`/config-env override in front drops the exemption and the push is denied. So does any step in the same command, before the push or after it, that can change where a push goes (`retargetsPush`): a `git config` write, `git remote add`/`set-url`/`rename`/`remove`, `git branch -u`, a redirect into a `.git/` path, a `.gitconfig`, the XDG `git/config` or a `GIT_CONFIG*` file, or any other command that names one in its words or takes the output of one through a pipe (`walkStep.pipedConfig`, as in `grep -l x .git/config | xargs sed -i`). A `readOnlyCommands` command (echo, printf, cat, head, tail, less, more, grep, rg without `--pre`, ls, stat, wc, diff, file) counts only through its redirects, and a `prose` step (a comment or text heredoc body) never counts. The resolvers read the config before the command runs, so they cannot see such a change. Adding a hint: implement the `Hint` interface in `internal/hint/`, register it in `hint.All` (`ForEvent` filters that list by event), and add a `[hints.<id>]` toggle to the consuming repo's config overlay. A hint returns `*Advice` or nil: there is no way for it to deny. `Advice.Tags` labels the fire's events entry; `hook.adviceTags` keeps `hint`, `event` and the session identity tags out of a hint's reach. Tag names a consumer reads are listed in `docs/hooks.md` ("Tags on hint events").

**Custom hints** are the hint-side twin of custom guards. A `custom_hints` entry in the belt config registers a named hint that execs an external command. The command gets the hook payload fields as JSON on stdin (`{"event","cwd","session_id","transcript_path"}`, plus `agent_id`/`agent_type` inside a subagent). Its stdout becomes the advice, prefixed `belt[<name>]:`, with trailing whitespace trimmed and multiple lines kept. A non-zero exit, a run past the budget (400 ms by default, `timeout_ms` per hint), a start failure, or empty stdout is silence plus a warn event. A broken external therefore never breaks a session. `event` accepts `session-start` and `subagent-start` (`config.CustomHintEvents`). It stays a string so prompt and post-tool events can join without a schema break, and validation rejects anything else by name. Validation also rejects an empty `command` and a name that shadows a built-in hint. `config.HintFields` is the list it checks, and a hint package test pins that table to `hint.All`.

`enabled` and `exclude_repos` sit on a custom hint's entry, and a `hints.<name>` toggle of the same name is honored too. Custom hints run after the built-ins, alphabetical by name, through the same `belt hint session-start` and `belt hint subagent-start` entrypoints. No built-in hint runs on subagent-start: a subagent brief comes from the consuming repo's config. An optional `agent_types` list gates a subagent-start hint to the subagent types it names (`Custom.admitsAgent`, through `config.MatchAgentType`: exact, or by prefix for an entry ending in `*`). An unlisted spawn skips the exec and logs no warn event, since declining there is configured, not a failure. `CustomHint.UnmarshalYAML` records whether the key was written, so `agent_types:` with no value fails validation instead of reading as unset. `hook.hintAdviceByEvent` maps each start event to the hookEventName its envelope must carry (SessionStart, SubagentStart). `belt doctor` lists them with their budget and an executable check. The first consumer is a machine-private hint (a daily journal) that a private config overlay registers on one machine class. That is what keeps it out of this public repo.

### Ledger and watcher

`belt record <event>` (`internal/ledger`, `hook.RunRecord`) posts one events entry per lifecycle hook: subagent-start, subagent-stop, task-completed, teammate-idle, permission-denied, notification, pre-compact, post-compact, session-end, stop-failure (`ledger.Events`). Source `belt-ledger` (`ledger.source`), level info (stop-failure is warn for the transient error types in `ledger.transientErrors` and error for the rest), title with a qualifier, message capped at 500 bytes on a rune boundary, tags for every set field including `repo`/`worktree`/`canonical`/`branch` from `gitloc.LocationAt` (the shared `kit/gitloc` package). It takes no writer, recovers its own panics, and exits 0 for a valid event whatever happens: SubagentStop output keeps the subagent running, and TaskCompleted/TeammateIdle/PreCompact block on exit 2. A broken config records with the defaults and tags the entry. Never wire it on WorktreeCreate/WorktreeRemove: those hooks replace Claude Code's git worktree handling.

Two tags need care. `worktree` is the linked worktree's toplevel for the payload cwd, never the cwd itself, and on a spawn that cwd can be the parent's. A subagent-start entry whose `agent_type` matches a `ledger.agent_types` key also gets `model` and `effort` (`ledger.declaredTags`). The same `config.MatchAgentType` decides as for the hint gate: the exact key wins, then the longest key ending in `*`. A named spawn reports its name as its `agent_type`, which is why a key for named spawns ends in `*`. The map restates the agent definition; belt never infers a value.

`belt watch` (`internal/watch`, `hook.RunWatch`) is off until `watch.enabled`. As an asyncRewake hook on Stop and SessionStart it polls `GET /api/events?source=belt-inbox&q=<session>&since=<cursor>` and keeps entries whose `to` tag equals the session id. On a hit it moves the cursor (`~/.cache/belt/watch-<session>`), prints the items on stderr and returns `errWake`, which `cli.Execute` maps to exit 2. Newest watcher wins through `watch-<session>.pid`. A cursor that cannot be written means no delivery, because a delivery without one would wake the session on every Stop. Every other outcome is exit 0, silent.

## pi package

`pi/` is a pi package (`pi/package.json`, `pi.extensions: ./extensions/*.ts`) that pi loads in place from the ralph sources cache; the consuming repo declares it in pi's `settings.json`, the same way it declares `mods/`. The README's pi section covers what each extension does and the `belt.json` keys. Working rules:

- The gate stays fail-closed: a missing belt, a failed `belt check`, and an unreadable `belt.json` (a dangling symlink included) all block (reads excepted for the last). pi-mcp-adapter resolves tool names loosely: `server` is optional on the `mcp` proxy, an `mcp__<server>` namespace proxy takes the same `{ tool, args }`, and a name may carry a display or legacy server prefix. So the gate reads a call every way the adapter could run it, and each check takes the strictest reading. A proxy call it cannot place on a server still runs `belt check external-text`. The prefix and namespace forms are ported from the adapter's `types.ts`; keep them in step when the adapter changes them. The adapter's `mcpScript` makes its MCP calls inside the adapter, where no `tool_call` event fires, so every `mcpScript` call asks whatever the allow list says (headless with no broker, a block). The hints and the ledger records fail open. `belt:deny` (`{ kind, target, reason }`) is a contract with the session-band mod's pi face; keep the name and the three keys. Never announce a denial that is not belt's on it, since session-band counts every one as belt's. The ledger listens to `belt:permission-denied` (`{ source, reason, toolName, toolCallId }`) instead. The gate announces it through `announceDenial` for a belt guard, a settings deny rule, or the user. A broker decision counts as the user's only when its reason is `DENIED_BY_USER`, the broker's own constant.
- `belt-hooks.ts` maps pi events onto Claude Code hook payloads. The README's pi section has the table of which pi event records which ledger event. A record never waits. Its payload goes to a temp file that becomes the stdin of a detached, unref'd `belt record`, so a quitting pi can't cut it short. A spawn error, a missing belt included, is dropped. stop-failure records on `agent_settled`, not `agent_end`, because pi can retry a failed run after `agent_end`. The read hint sends pi's `read` as a Claude `Read`: an absolute `file_path`, `offset` and `limit` as given, and `tool_response: { type: "text", file: { totalLines } }`. On an unranged read `totalLines` comes from the result's truncation details. Otherwise the extension counts the file on disk the way pi does, splitting on `\n`. A `csl_read` goes to belt as-is, with its content blocks as the response. No hint runs for a call with a `parentToolCallId`, since a codemode script made it. stop-failure's `error` comes from `failureType`, a pure function with its own table test. It may return only types in the ledger's StopFailure vocabulary (`internal/ledger`), and `unknown` when the text is not clear.
- `belt.json` keys add to or override the defaults: the server lists only grow, and an `mcpPrefixes` entry can remap a default prefix. Unknown keys are ignored but named in the gate's config line, so a misspelt key shows up. The defaults name only this repo's servers and github.com. A machine's own server or sandbox variable belongs in the consuming repo's rendering of the file, never in `lib/config.ts`.
- `permission-broker.ts` keeps its env var names and `Symbol.for` keys. An extension outside this package may import its own copy, and the shared state on `globalThis` keeps a second load idempotent.
- Tests run with `make test-js` (`node --test pi/test/*.test.mjs`); `make test` runs them after the Go tests, and CI runs `make test-js` in the belt job. Each file runs in its own process because both extensions remember a missing belt for the process lifetime. For the same reason, pi picks up a belt installed mid-session only on its next start. For a load check without touching real pi state, run `pi -p --no-session --offline -e pi "hi"` with `PI_CODING_AGENT_DIR` pointed at a scratch dir. With no credentials there the run stops at "No API key found", and a load error prints before that line.
- pi loads nothing and prints nothing for a declared package path that does not exist. So the gate sets `globalThis[Symbol.for("mad01.pi.belt-gate")]` while it is live: at load and at session start, cleared at session shutdown. The consuming repo ships a small extension of its own that blocks every tool call while the marker is missing. Keep the key; it is that extension's contract. The consuming repo also checks the path itself (a ralph `[[tools]]` check), since pi never complains.

## Gotchas

- **The bash-command parser is token-based, not a shell parser.** It splits on `&&`/`||`/`;`/`|`/newlines and matches bare `git … push` sequences. The git guards (`git-push-main`, `git-discard`) and `script-deny-list` read a quote-aware walk (`shellread.go`/`shellwalk.go`) over subshells, `$(…)`/backtick substitutions, `sh -c`, `eval`, `\`-continuations and `{ … }` groups, so a wrapped push or a message that only names a command is read the way the shell runs it. A shape the walk cannot read gets the full walk up to the line it fails on and a fail-closed read of the rest. Elsewhere the token split still holds, and belt is a guardrail against habit, not an adversary-proof sandbox. A shell-text walk cannot be complete. git-push-main still misses a push through an alias set before the command (a config file, `~/.gitconfig`), written by anything but `git config`, or named at run time (`-c "$K=push"`). It also misses a script file already on disk, an interpreter that builds the words `git` and `push` at run time, `ssh`, `xargs sh -c` and `trap` bodies, and shell `alias` definitions.
- **`publish-internal-names` scans whole command text on purpose.** A heredoc PR body spans several line segments. So a commit, tag, or gh call is checked against the entire bash command plus the files it names, not one flag value. A path elsewhere in the same command that carries an internal name therefore denies too. That is a true positive in a public repo, since the path is about to be public. Push checks shell out to git per pushed branch (remote URL, base ref, `git log -z`). So the guard costs one or two git calls only when a command actually pushes, commits, or calls gh in a github.com repo.
- **Same for `script-deny-list`.** `curl | bash`, list-form `subprocess.run`, quoted tokens, line continuations, same-command write-then-run, command substitution (`$(…)`, scanned wherever it stands), an `echo`/`printf` piped into an interpreter, a download or decoded text run as code in the shapes the row above lists (a variable set to one and a file the same command saves one to included), a command behind a wrapper (`coproc` and zsh's `noglob` too) or a reserved word, and a command a variable, alias or function in the same command names are covered now. A carrier command's own text is masked first, so a denied command named only in an `echo` string or a commit message, even after an earlier `bash -c`, passes instead of a false deny. Still slipping through: an alias or function defined outside the command (a shell startup file), a script file run inside a `-c` string (`bash -c 'bash x.sh'`), the download shapes the row above lists as not read yet, a variable from the profile whose name does not say what it runs (`$X -rf /x`), text the shell decodes itself (`printf '\x72\x6d'`, `$'…'`) or a transform such as `tr` or `rev` into a shell, a file an earlier command made executable, run later with no shebang, an rm option only an expansion supplies (`rm -r $F`, left out since a `$X` read as an option would deny every `rm -f "$file"`), and a quote inside the command name (`r''m`). rm options in any spelling (`rm -r -f`) and the flags before a kubectl, gcloud or terraform verb match on argv now. Flag reordering for any other tool (`git -C x remote prune`) is an `extra_patterns` job: use a `re:` pattern rather than enumerating literal variants.
- **Runtime debugging lives in `operating.md`** (embedded in the binary, printed by `belt docs`): the no-daemon execution model and changes-apply-immediately behavior, the config fallback and fail-closed/fail-open matrix, deny false-positive paths, version-skew checks. Keep those facts there, not here.
- **`prefer-csl` does not reuse `guard.splitSegments`.** That splitter preserves byte offsets and treats `|` exactly like `&&`, which is right for finding a denied command anywhere in a pipeline and wrong for this hint. Telling a pipe filter apart from a standalone search is its entire precision requirement. The hint has its own quote-aware splitter so a `|` inside a grep pattern does not read as a pipe.
- **Version probe convention.** `belt version -o json` returns the shared four-key build metadata object (`version`, `commit`, `tag`, `build_time`, every key present and `""` when unknown) from `github.com/mad01/thismoon/buildinfo`, injected by `buildinfo.mk` at link time. Plain `belt version` stays a bare token — ralph and status parse it as one. `belt doctor` opens with the same metadata, so a doctor report always names the binary that produced it.
- **Keep literal internal hostnames and org names out of belt's own source and docs.** This repo is public and the suspenders pre-commit guard blocks them. Which repos are public-bound is enumerated in the rendered config's `public_repos` list (docs/adr/0015); the derived `github.com` rule is only the fallback for a config without the key. The list itself lives in the consuming repo, never here.
